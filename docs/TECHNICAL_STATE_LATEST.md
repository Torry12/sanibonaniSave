# 🚀 Current Technical State: October 2026 (verified 2026-10-30)

This document serves as the authoritative, up-to-date record of the `SanibonaniSave` platform architecture following the comprehensive refactoring, hardening, and testing phases finalized in October 2026.

---

## 1. 🏗️ Architecture & State Management

### 1.1 Strict Null-Safety & Robust Error Boundary
We have eliminated unsafe unboxing assertions across the presentation, domain, and data layers.
- **View Models:** Safe navigation fallbacks and robust state flows (`val groupId = group.id ?: return`).
- **Repositories & Mappers:** Fault-tolerant deserialization with `try/catch` wrappers.

### 1.2 Coroutine & Synchronization Resilience
- **CancellationException Intercepts**: Broad `catch (e: Exception)` blocks across `BaseRepository`, `SyncRepositoryImpl`, and `RealtimeSyncManager` explicitly verify and rethrow `CancellationException`.
- **Multiplexed WebSockets**: `RealtimeSyncManager` utilizes a unified, multiplexed Supabase realtime channel across all core database tables (`contributions`, `payments`, `loans`, `loan_repayments`, `group_ledger`, `notifications`, `payouts`, `beneficiaries`, `member_documents`, `beneficiary_payout_claims`, `groups`, `members`, and `bank_transactions`).

### 1.3 Module Boundary Now Fully Held
- **`:domain` is pure**: no `io.github.jan.supabase.*` and no `android.*` imports remain in `domain/src/main`. Models are `@Serializable` only — `@Parcelize` was dropped, so navigation passes ids and the screens re-load the model. Logging crosses the boundary through the `AppLogSink` port, with the `android.util.Log` implementation supplied from `:app`.
- The module is still an Android library (`com.android.library`) for `BuildConfig.PLATFORM_ADMIN_EMAIL` and the instrumentation runner; that is a build-script concern, not an import leak. `DomainModuleBoundaryTest` keeps it that way.
- **Validation ownership**: `InputValidator` is the single rule owner (SA ID Luhn + real date of birth, phone, bank account, branch code, card/expiry/CVV, names, emails). `ValidationUtils` is the caller-facing convenience surface and delegates every rule to it — it must never restate a rule with its own regex.

## 2. 💸 Financial Engineering, Fees & Burial Policy Controls

### 2.1 The `Money` Domain Pattern
- All financial math strictly uses the immutable `Money` (`BigDecimal`) domain model and `Money.ratio()`. Never use `Double` for currency storage or math.

### 2.2 Multi-Tier Payout & RPC Resilience
- **Atomic Completions**: `process_complex_payment_v4` executes with row-level database locking (`FOR UPDATE`).
- **Validate Before Write**: the contribution, platform-revenue and ROSCA-payout RPCs reject a non-positive amount, a third decimal place, or an unknown `status`/`type` with `[FIN_003]` before touching a row, so an outbox retry can never half-apply garbage.
- **Flexible PostgREST Ingestion**: Data source implementations utilize `.decodeAs<JsonElement>()` with pattern matching for `JsonObject` and `JsonArray` payload containers.
- **Settlement Closure**: `settle_expired_loan_v2(UUID)` is the single guarded entry point for closing an expired loan; the caller-supplied `record_loan_settlement_extraction_v1` is revoked from every role.

### 2.3 Burial Society Policy Controls & Fee Precision
- **Configurable Burial Policies**: Group admins can set `burialClaimAmount`, `minMembersForClaims`, and `minReservePercentage` via the Admin Portal Settings tab.
- **Automated Eligibility Enforcement**: `ValidateBurialClaimEligibilityUseCase` automatically enforces member tenure, active membership thresholds, and reserve adequacy ratios.
- **Accurate Overdue & Platform Fee Math**: Overdue amounts evaluate net unpaid shortfalls, and platform fees utilize configured global platform rates (`config.monthlyMemberFee`).

All six use `enqueueUniquePeriodicWork` with `ExistingPeriodicWorkPolicy.KEEP`; the four per-group workers are named `"${WORK_NAME}_$groupId"` — `FeeEnforcementWorker` and `LedgerConsistencyWorker` used to enqueue under the shared `WORK_NAME` (the fee one with `UPDATE`), so only the last group written into that slot was ever processed. `AutomatedGovernanceWorker` and `LoanSettlementWorker` had no `schedule()` at all before this; every companion now takes `WorkManager` rather than a `Context`, supplied by `AppModule.provideWorkManager` (the manifest removes the default `WorkManagerInitializer`, so the refresh runs on `Dispatchers.IO` to keep on-demand initialisation off the main thread). Gap covered by `BackgroundWorkSchedulerTest` (8 cases). Signing out does not cancel another identity's schedules, and a group created mid-session waits for the next hydration — `WorkInfo` carries no input to recover names from, and neither case costs behaviour: entitlement is decided by the `SEC_002` guards and RLS, the stale jobs only add a refused call per group per day, and a brand-new group has no ledger, members or fee period to act on. See `docs/BUSINESS_PROCESSES.md` §4.
