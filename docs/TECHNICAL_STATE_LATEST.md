# 🚀 Current Technical State: October 2026 (verified 2026-10-28)

This document serves as the authoritative, up-to-date record of the `SanibonaniSave` platform architecture following the comprehensive refactoring, hardening, and testing phases finalized in October 2026.

---

## 1. 🏗️ Architecture & State Management

### 1.1 Strict Null-Safety & Robust Error Boundary
We have eliminated unsafe unboxing assertions across the presentation, domain, and data layers.
- **View Models:** Safe navigation fallbacks and robust state flows (`val groupId = group.id ?: return`).
- **Repositories & Mappers:** Fault-tolerant deserialization with `try/catch` wrappers.

### 1.2 Coroutine & Synchronization Resilience
- **CancellationException Intercepts**: Broad `catch (e: Exception)` blocks across `BaseRepository`, `SyncRepositoryImpl`, and `RealtimeSyncManager` explicitly verify and rethrow `CancellationException`.
- **Multiplexed WebSockets**: `RealtimeSyncManager` utilizes a unified, multiplexed Supabase realtime channel across all core database tables (`contributions`, `payments`, `loans`, `loan_repayments`, `group_ledger`, `notifications`, `payouts`, `beneficiaries`, `member_documents`, `beneficiary_payout_claims`, `groups`, `members`, and `bank_transactions`).

### 1.3 Module Boundary Now Fully Held
- **`:domain` is pure**: no `io.github.jan.supabase.*` and no `android.*` imports remain in `domain/src/main`. Models are `@Serializable` only — `@Parcelize` was dropped, so navigation passes ids and the screens re-load the model. Logging crosses the boundary through the `AppLogSink` port, with the `android.util.Log` implementation supplied from `:app`.
- The module is still an Android library (`com.android.library`) for `BuildConfig.PLATFORM_ADMIN_EMAIL` and the instrumentation runner; that is a build-script concern, not an import leak. `DomainModuleBoundaryTest` keeps it that way.
- **Validation ownership**: `InputValidator` is the single rule owner (SA ID Luhn + real date of birth, phone, bank account, branch code, card/expiry/CVV, names, emails). `ValidationUtils` is the caller-facing convenience surface and delegates every rule to it — it must never restate a rule with its own regex.

## 2. 💸 Financial Engineering, Fees & Burial Policy Controls

### 2.1 The `Money` Domain Pattern
- All financial math strictly uses the immutable `Money` (`BigDecimal`) domain model and `Money.ratio()`. Never use `Double` for currency storage or math.

### 2.2 Multi-Tier Payout & RPC Resilience
- **Atomic Completions**: `process_complex_payment_v4` executes with row-level database locking (`FOR UPDATE`).
- **Validate Before Write**: the contribution, platform-revenue and ROSCA-payout RPCs reject a non-positive amount, a third decimal place, or an unknown `status`/`type` with `[FIN_003]` before touching a row, so an outbox retry can never half-apply garbage.
- **Flexible PostgREST Ingestion**: Data source implementations utilize `.decodeAs<JsonElement>()` with pattern matching for `JsonObject` and `JsonArray` payload containers.
- **Settlement Closure**: `settle_expired_loan_v2(UUID)` is the single guarded entry point for closing an expired loan; the caller-supplied `record_loan_settlement_extraction_v1` is revoked from every role.

### 2.3 Burial Society Policy Controls & Fee Precision
- **Configurable Burial Policies**: Group admins can set `burialClaimAmount`, `minMembersForClaims`, and `minReservePercentage` via the Admin Portal Settings tab.
- **Automated Eligibility Enforcement**: `ValidateBurialClaimEligibilityUseCase` automatically enforces member tenure, active membership thresholds, and reserve adequacy ratios.
- **Accurate Overdue & Platform Fee Math**: Overdue amounts evaluate net unpaid shortfalls, and platform fees utilize configured global platform rates (`config.monthlyMemberFee`).

## 4. 🗃️ Backend & Database Synchronization

### 4.1 Supabase Ground Zero Schema & Seed Pipeline
- Fully consolidated schema (`01_DATABASE_SCHEMA.sql`, `GROUND_ZERO.sql`, and `SEED_ALL_DATA.sql`) with automated migration runners (`supabase db reset --local` and linked online sync).
- Master seed data pre-populates 8 authoritative group types, 24 persona members, 12 months of ledger history, and **15 valid simulation burial claims**.

### 4.2 Financial SQL Hardening (October 2026)
- **Tier state as measured 2026-10-28**: `SYNC_DELTA_20261014`, `_20261021`, `_20261022`, `_20261026`, `_20261026B`, `_20261027` and `_20261028` are applied on **Local**. Cloud is user-run from the Dashboard and still owes `_20261027` and `_20261028`; each file's `P.0` read-only pre-flight runs first. `_20261029` and `_20261029B` are cut from the masters and applied on **neither** tier, so Local and Cloud are both behind the repo on the money RPCs. Schema parity is measured with `supabase/maintenance/SCHEMA_PARITY_DIGEST.sql` (Local currently `1032|…F=83…|9752967a0c8a1e095d1de650a6132efb`, expected `F=84` after `_20261029` and `F=87` after `_20261029B`) and per-object bodies with `SCHEMA_OBJECT_FINGERPRINTS.sql`.
- `groups.balance` is `NUMERIC(12,2) NOT NULL DEFAULT 0`. The 20261022 delta repaired every NULL from that group's own ledger, set the constraint, and wrapped both spend guards (`approve_and_disburse_loan_v2`, `complete_payout_v2`) in `COALESCE(v_group.balance, 0)` so a missing balance can no longer skip the liquidity check.
- The 20261021 delta hardened the core RPCs: groups-first `FOR UPDATE` lock ordering, advisory-lock idempotency for platform revenue, a set-based running-balance recompute, real `discrepancy_found` reporting in `recalculate_all_group_financials_v3`, eight hot-path indexes, and pinned `search_path` on the remaining unpinned `SECURITY DEFINER` functions (18 updated; post-check `targets_unpinned=0`). 20261026 pinned the two money RPCs the first pass missed (`increment_group_balance`, `pay_platform_fee_v2`), and 20261026B added the four `*_status` evidence columns to `beneficiary_payout_claims`.
- 20261027 moved the audit reports behind server-side identity checks (`[SEC_002]`), collapsed the platform report to one pass per table, and withdrew `EXECUTE` from `PUBLIC` and `anon` for all four. 20261028 put `[FIN_003]` validation ahead of every write on the contribution/revenue/ROSCA path and closed the loan-settlement gap: `settle_expired_loan_v2(UUID)` is the only settlement entry point, `record_loan_settlement_extraction_v1` is revoked from every role, and a non-admin, non-group-admin caller is refused.
- 20261029 (masters, not yet applied anywhere) does for the money path what 20261027 did for the audit path. Twelve RPCs carry the shipped `service_role OR is_platform_admin OR is_group_admin(...)` identity check (`[SEC_002] *_ACCESS_DENIED`), with `is_own_member(UUID)` added so a member paying their own contribution or repayment is not refused two frames into a nested call — `auth.uid()` and `auth.role()` read the session JWT, which survives into the inner frame, so a guard that only admitted admins would break the member flows. `automate_monthly_billing_v1` conditions its guard on `auth.jwt() IS NOT NULL` so the `pg_cron` run, which carries no JWT, is never asked who it is. `approve_and_disburse_loan_v2` and `complete_payout_v2` now record the session identity in `reviewed_by`/`processed_by` instead of the `p_admin_id` the caller typed. `reconcile_bank_transaction_v1` finally codes its not-found (`[SYS_001]`). Privileges are withdrawn in two tiers: `anon` and `PUBLIC` lose execute across the whole money surface, and the eight ledger primitives and maintenance jobs (`increment_group_balance`, `recompute_ledger_running_balances_v2`, `perform_group_reconciliation_v1`, `consolidate_group_ledger_v1`, `create_ledger_checkpoint_v1`, `automate_monthly_billing_v1`, `simulate_bulk_activity_v2`, `record_platform_revenue_v1`) lose `authenticated` too — a nested call inside a `SECURITY DEFINER` wrapper is authorised against the wrapper's owner, so closing the HTTP door breaks no wrapper. `search_members_v1` gains `PLATFORM_ADMIN_ONLY` and the `behavior_score` key the console renders.
- 20261029B (masters, not yet applied anywhere) declares the three RPCs `:data` has always called by name with nothing behind them — `close_poll_v1`, `pay_burial_claim_v1`, `record_disbursement_v1` — which `SYNC_DELTA_20261021` K.4.e recorded as a still-open gap and deliberately did not close. Nothing was invented to make a call resolve: `pay_burial_claim_v1` is the state machine `ProcessBurialClaimUseCase` already runs, moved to where the server decides final truth (claim lookup → groups `FOR UPDATE` → `[SEC_002]` → payable-from-`submitted`/`under_review`/`approved` → `[FIN_003]` → `[SEC_001]` MFA → `[FIN_001] NO_CASH`), and its ledger row is category `claim`, description `'Burial claim: ' || beneficiary_name`, `transaction_id` = the claim id, i.e. the exact row `consolidate_group_ledger_v1` reconstructs, so live writes and ledger rebuilds cannot diverge and a replayed call cannot debit twice. `record_disbursement_v1` is a guard plus a sign check around `increment_group_balance` — the primitive keeps the lock, the `[SYS_002]` idempotency key and the insufficient-funds check — and it exists precisely because 20261029 withdrew that primitive from `authenticated`: a `SECURITY DEFINER` wrapper is authorised against its owner role, so this is the one route by which a signed-in group admin may still book an outflow. `close_poll_v1` is the first early-close path at all; until now `tr_sync_poll_status` at `ends_at` was the only way a poll ended, and it never touched `vote_count`, which stays owned by `tr_sync_poll_vote_count`. All three carry the shipped `service_role OR is_platform_admin OR is_group_admin(…)` check with no `is_own_member` allowance (closing a poll, paying a claim and booking a disbursement are never self-service), and `pay_burial_claim_v1` drops the nil-UUID `p_admin_id` the platform console sends before writing `reviewed_by`, because that sentinel is not a row in `auth.users` and the column has a foreign key there.
- **Consequence on the client**: the simulation harness calls `increment_group_balance` by name in six debug/androidTest places (`LiveSimulationRunner.kt:617` seeds liquidity, `:390`/`:452`/`:536` hand-debit after a disbursement RPC fails and force the row status, plus `LiveFinancialFlowSimulation.kt:78` and `BusinessProcessSimulationTest.kt:322`); all sign in as an admin, so they run as `authenticated` and get 403 against a tier that has run 20261029. Production code is unaffected — `GroupRepositoryImpl`/`GroupFinancialRepositoryImpl` only serve `BalanceAdjustmentOutboxHandler`, and nothing enqueues that operation. Re-pointing the harness and deleting the dead path is open work. The three flows 20261029B declares also moved client-side: `VotingRepositoryImpl.closePoll` refuses a blank poll id instead of posting `""` (a UUID cast error, not a decision), `GroupVotingViewModel.closePoll` reports the refusal instead of dropping it (it had only an `onSuccess`, so the button looked dead), and the disbursement/claim payloads are built by named companions with the RPC name pinned, the pattern `SupabasePayoutDataSourceImpl.buildRoscaPayoutRpcParams` already uses. The voting screen still renders Close to every viewer — the database decides, and the refusal now reaches the state the screen reads.
- **Verification hazard recorded in the delta**: executing these `SECURITY DEFINER` RPCs as `anon` crashes the Local Postgres 17.6.1 image (signal 11) — over SQL and over the PostgREST route alike. Prove a revoke with `has_function_privilege`; the `curl` leg is cloud-only. The `settle_expired_loan_v2` HTTP route is therefore still unverified on both tiers — it needs a real user JWT through the app.
- **Open SQL gaps (documented, not papered over)**: the three named-but-undeclared RPCs are declared in the masters and cut as 20261029B, so the gap that remains is tier state — until 20261027 → 20261028 → 20261029 → 20261029B have been applied, closing a poll, paying a burial claim and booking a disbursement still fail with `PGRST202` against both tiers. `settle_expired_loan_v2`'s HTTP route is still unverified because it needs a real user JWT. The anonymous-execute gap this file used to record on `internal_post_contribution`, `record_contribution_v2`, `record_platform_revenue_v2` and `process_rosca_payout_v3` is closed in the masters by 20261029 and stays open **on the tiers** until that delta is applied.
- **Closed client↔tier table gaps** (three phantom reads found by diffing every `postgrest["…"]` key in `:data` against `01_DATABASE_SCHEMA.sql`): DYNAMICS now reads `member_behavior_track` (the table, not the invented `member_behavior_tracks`); `getCloudBackups` lists the `backups` storage bucket instead of a `database_backups` table no master defines, and reports an outage as a failure instead of folding it into `emptyList()`; `SyncRepositoryImpl` retries claims under `beneficiary_payout_claims`, not `burial_claims`. Platform member search no longer queries the phantom `platform_member_behavior_insights_v1` view — it calls the `search_members_v1` RPC that has always carried the answer, which is why that RPC had to gain `behavior_score`.
- **Open client↔tier RPC gap**: `triggerCloudBackup()` and `computeSystemWideMetrics()` point at `trigger-backup` and `compute-platform-metrics` edge functions; `supabase/functions/` defines neither, so both fail against a real deployment.
- **Background work is scheduled**: `app/…/worker/BackgroundWorkScheduler.refresh()` is invoked by `AuthViewModel` when the hydrated session flow emits `Success` (cold start with a stored session and fresh sign-in both reach it). It enqueues `ProbationCompletionWorker` for any signed-in session, `AutomatedGovernanceWorker` + `LoanSettlementWorker` only for `UserRole.PLATFORM_ADMIN` (both read every group through `PlatformRepository.getAllGroups`), and per administered group a `LedgerConsistencyWorker` and `FeeEnforcementWorker`, adding `AutomatedRoscaWorker` for `GroupType.ROSCA`. All six use `enqueueUniquePeriodicWork` with `ExistingPeriodicWorkPolicy.KEEP`; the four per-group workers are named `"${WORK_NAME}_$groupId"` — `FeeEnforcementWorker` and `LedgerConsistencyWorker` used to enqueue under the shared `WORK_NAME` (the fee one with `UPDATE`), so only the last group written into that slot was ever processed. `AutomatedGovernanceWorker` and `LoanSettlementWorker` had no `schedule()` at all before this; every companion now takes `WorkManager` rather than a `Context`, supplied by `AppModule.provideWorkManager` (the manifest removes the default `WorkManagerInitializer`, so the refresh runs on `Dispatchers.IO` to keep on-demand initialisation off the main thread). Gap covered by `BackgroundWorkSchedulerTest` (8 cases). Signing out does not cancel another identity's schedules, and a group created mid-session waits for the next hydration — `WorkInfo` carries no input to recover names from, and neither case costs behaviour: entitlement is decided by the `SEC_002` guards and RLS, the stale jobs only add a refused call per group per day, and a brand-new group has no ledger, members or fee period to act on. See `docs/BUSINESS_PROCESSES.md` §4.
- Changes to an existing tier go through a new dated delta only; applied deltas are frozen so their stored `prosrc` fingerprints stay verifiable.
